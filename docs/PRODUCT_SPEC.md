# It Girl Planner — продуктовая спецификация и модель данных

Версия: 0.1  
Этап: 2 — спецификация и модель данных  
Статус: согласованы базовые правила целей, прогресса и наград XP; детали интерфейса остаются соответствующим этапам.

## 1. Назначение

It Girl Planner — личное приложение для ведения целей, измерения их прогресса, планирования задач и развития персонажа Maddy. Данные относятся к одному аккаунту и синхронизируются между устройствами через Supabase. У каждого значения есть реальный источник; демонстрационные цели, задачи и XP не создаются.

Первый релиз остаётся узким: цели, Key Results, задачи календаря, сводка и журнал XP. Уведомления, TickTick, настраиваемые темы и резервные копии не входят в обязательный объём.

## 2. Согласованные продуктовые решения

- У цели два статуса: **активна** и **выполнена**. Отдельных статусов паузы и архива нет.
- Удаление цели — полное и необратимое, с явным подтверждением. Связанные Key Results и записи прогресса удаляются; задачи планировщика сохраняются и отвязываются от цели.
- Прогресс цели рассчитывается из Key Results с весами. Если Key Results нет, прогресс равен 0%.
- Задачи и выполненные Key Results дают XP Maddy. Каждое событие начисления учитывается один раз; повторная доставка того же события не начисляет XP повторно.
- XP за выполнение самой цели не начисляется.
- Точные величины XP и таблица уровней будут сбалансированы в этапе 8; они не хранятся как предположение в UI.

## 3. Основные сценарии

1. Пользователь входит в аккаунт и видит только свои данные.
2. Создаёт цель с названием, необязательным описанием и сроком.
3. Добавляет к цели измеримые Key Results и задаёт вес каждого результата.
4. Обновляет фактическое значение Key Result; прогресс цели пересчитывается.
5. Планирует задачу на календарную дату, при желании связывает её с целью и отмечает выполненной.
6. Сводка показывает активные цели, ближайшие задачи и текущую неделю из тех же записей, что и профильные разделы.
7. Maddy получает XP из подтверждённых событий выполнения; журнал объясняет источник каждого начисления.
8. Пользователь может изменить статус цели на «выполнена» или удалить её с подтверждением.

## 4. Правила расчёта прогресса

У Key Result есть направление измерения, исходное значение, целевое значение и положительный вес. Для числового результата доля выполнения:

- рост: `clamp((текущее - исходное) / (целевое - исходное), 0, 1)`;
- снижение: `clamp((исходное - текущее) / (исходное - целевое), 0, 1)`.

Значения, уже достигшие или превысившие цель в заданном направлении, ограничиваются 100%; движение в противоположную сторону не даёт отрицательный прогресс. Для бинарного результата значение 0 или 1 даёт 0% или 100%.

Общий прогресс цели — взвешенное среднее долей Key Results, выраженное в процентах и округлённое до целого для показа. Если у цели нет Key Results, показывается 0%. Статус «выполнена» меняет пользователь; достижение 100% не завершает цель автоматически.

У числового Key Result исходное и целевое значения должны различаться; вес должен быть положительным. Валидация не допускает деление на ноль.

## 5. Предлагаемая модель данных

Все пользовательские таблицы имеют UUID первичного ключа, временные метки `created_at`/`updated_at` там, где запись редактируется, и поле `user_id`, связанное с владельцем из Supabase Auth. Все выборки ограничиваются текущим пользователем через Row Level Security (RLS). Секретный `service_role` ключ не попадает в браузер; публичный клиентский ключ не заменяет RLS.

### `profiles`

- `user_id` — PK и FK к `auth.users.id`;
- `display_name` — необязательное отображаемое имя;
- `timezone` — IANA-имя часового пояса;
- `locale` — локаль интерфейса;
- `week_starts_on` — начало недели;
- `theme` — `dark` или `light`;
- `created_at`, `updated_at`.

Профиль создаётся безопасно при регистрации; не содержит паролей и секретов.

### `goals`

- `id`, `user_id`;
- `title` — обязательное название;
- `description` — необязательное описание;
- `category` — необязательная пользовательская метка, без заранее выдуманного списка категорий;
- `status` — `active` или `completed`;
- `start_date`, `due_date` — необязательные календарные даты;
- `sort_order` — порядок пользователя;
- `completed_at` — дата перехода в выполненное состояние;
- `created_at`, `updated_at`.

`due_date` не может предшествовать `start_date`, если обе даты заданы. Переключение обратно в `active` очищает `completed_at`. Удаление подтверждается и навсегда удаляет дочерние записи.

### `key_results`

- `id`, `user_id`, `goal_id`;
- `title` — обязательное название результата;
- `metric_type` — `numeric` или `boolean`;
- `direction` — `increase` или `decrease` для числовой метрики;
- `start_value`, `target_value`, `unit` — для числовой метрики;
- `weight` — положительный вес в прогрессе цели;
- `sort_order`;
- `created_at`, `updated_at`.

Владелец Key Result должен совпадать с владельцем цели. Для бинарного результата целевое состояние — выполнено/не выполнено.

### `key_result_updates`

- `id`, `user_id`, `key_result_id`;
- `value` — новое числовое значение или бинарное состояние;
- `note` — необязательная заметка;
- `recorded_at` — время/дата отметки;
- `created_at`.

История отметок хранится отдельно от определения результата. Текущее значение — последняя действующая отметка; если отметок нет, используется `start_value` или начальное значение `false`. Все значения принадлежат тому же владельцу, что и Key Result.

### `planner_tasks`

- `id`, `user_id`;
- `title` — обязательное название;
- `description` — необязательные детали;
- `goal_id` — необязательная связь с целью;
- `due_date` — календарная дата в локальном календаре пользователя;
- `start_at`, `end_at` — необязательные временные границы, если задача привязана ко времени;
- `completed_at` — null, пока задача не выполнена;
- `sort_order`;
- `created_at`, `updated_at`.

Повторяющиеся задачи не входят в первый вариант планировщика. Удаление задачи — явное действие. Если задача связана с удаляемой целью, связь удаляется вместе с целью, а задача также удаляется согласно выбранному выше правилу полного удаления дочерних записей.

### `maddy_xp_events`

- `id`, `user_id`;
- `planner_task_id` — необязательный FK к задаче;
- `key_result_id` — необязательный FK к Key Result;
- `event_type` — подтверждённое выполнение;
- `idempotency_key` — уникальный ключ одного события начисления;
- `xp_delta` — целое число;
- `created_at`.

Таблица является журналом: итоговый XP вычисляется из её записей, награда содержит ссылку на источник. Ровно одно из полей `planner_task_id` и `key_result_id` заполнено. Уникальность `idempotency_key` предотвращает двойное начисление при повторах того же события. Переход задачи или Key Result в выполненное состояние создаёт событие; повторный переход после отмены выполнения считается новым событием. Значения наград и переходов уровней задаются в этапе 8.

## 6. Связи

- `auth.users 1—1 profiles`;
- `profiles/user 1—N goals`;
- `goals 1—N key_results`;
- `key_results 1—N key_result_updates`;
- `profiles/user 1—N planner_tasks`;
- `goals 1—N planner_tasks` (необязательная связь задачи с целью; при удалении цели связь обнуляется, сама задача остаётся);
- `profiles/user 1—N maddy_xp_events`;
- XP-событие ссылается ровно на одну задачу или один Key Result как источник.

## 7. Доступ, целостность и даты

- RLS включён для всех таблиц пользовательских данных; чтение и запись разрешены только при совпадении `user_id = auth.uid()`.
- Для вложенных записей проверяется владение родителем, а не только переданный `user_id`.
- Внешние ключи, уникальные ключи идемпотентности и проверки значений обеспечивают целостность в базе, а не только в UI.
- Дни календаря и сроки — календарные даты в часовом поясе профиля. Временные отметки событий хранятся как `timestamptz` в UTC и форматируются локально.
- Потеря сети, истёкшая сессия и отсутствие данных должны иметь отдельные состояния; сбой сохранения никогда не отображается как успешное сохранение.

## 8. Что не входит в этап 2

Подключение Supabase, миграции, авторизация, CRUD и UI-реализация принадлежат следующим этапам. Здесь нет SQL, ключей, вымышленных записей и начислений. Повторяющиеся задачи, уведомления, TickTick, пользовательский конструктор тем и резервные копии требуют отдельных продуктовых решений.

## 9. Критерии завершения этапа 2

- Статусы цели, удаление, способ расчёта прогресса и источники XP отражают решения пользователя.
- Сущности и связи покрывают цели, Key Results и их историю, задачи календаря, профиль и журнал XP.
- Для пользовательских таблиц описаны владение, ограничения и требования RLS.
- Повторяющиеся задачи, уведомления, TickTick и пользовательские темы не попали в MVP по умолчанию.
